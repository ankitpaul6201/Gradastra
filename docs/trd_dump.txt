This TRD converts the Gradastra PRD into implementable technical requirements. It defines a recommended stack, system boundaries, data model, API contracts, third-party services, workflows, security controls, deployment approach and acceptance criteria. The team must verify current vendor pricing, regional availability, terms, data-processing agreements and API limits before committing.
1. Technical Goals and Constraints
Deliver a responsive, accessible, SEO-friendly global education platform.
Support public university discovery without mandatory login.
Support authenticated students, verified advisors, moderators and administrators.
Keep consultations free and prevent any commission or paid-placement logic from entering the product.
Distinguish official information, independently checked facts, student-reported experiences and opinion.
Protect student identity and enrollment documents; never expose verification documents publicly.
Launch with a focused, maintainable system that a small engineering team can operate.
Support multiple countries, campuses, currencies, academic calendars, degree structures and time zones.

3.1 Architectural requirements
Use a modular monolith with clear domain boundaries and dependency direction.
Keep business rules in server-side domain/service modules, not UI components.
Use server-side authorization for every protected read and write.
Use database transactions for multi-record state changes.
Use asynchronous jobs for non-critical external calls and retries.
Keep provider integrations behind adapter modules so vendors can be replaced.
Do not expose service-role keys, database credentials or private storage credentials to the browser.
Use a separate staging environment and production environment.

5.2 UI and accessibility
Mobile-first responsive layouts; core flows must work at narrow phone widths.
Target WCAG 2.2 AA: keyboard navigation, visible focus, semantic headings, labels, contrast and accessible errors.
Use loading, empty, error, success and permission-denied states for every data-driven view.
Use pagination or cursor-based loading for large directories and review lists.
Do not communicate status through colour alone.
Use optimistic UI only where rollback is safe; consultation state changes should reflect server confirmation.
Keep public university content server-rendered and indexable; private dashboard content must not be indexed.
5.3 Design system
Define semantic design tokens for colour, typography, spacing, radii and elevation.
Use consistent components for university cards, source labels, verification badges, review summaries and consultation states.
Provide explicit labels for 'Officially published', 'Independently checked', 'Student-reported', 'Personal opinion' and 'Not verified'.
Do not use an aggregate quality score until its methodology, minimum sample rules and bias controls are documented.
6. Backend and API Design
Use versioned JSON REST endpoints under /api/v1 for public and authenticated product operations. Next.js route handlers may implement these initially. Use OpenAPI 3.1 to document contracts. Internal domain services should not depend on HTTP request objects.
6.1 API conventions
JSON request and response bodies; UTF-8.
Use UUID identifiers or opaque stable IDs; never expose sequential database IDs.
Use ISO 8601 timestamps in UTC and store the user's IANA time zone separately.
Use ISO 4217 currency codes and store monetary amounts as decimal values, not floating-point numbers.
Validate all inputs with Zod or equivalent on the server.
Use cursor pagination for growing collections; enforce maximum page sizes.
Return consistent error envelopes with a stable machine-readable code and safe message.
Use idempotency keys for operations where duplicate submissions would be harmful.
Apply rate limits to login, advisor requests, reviews, messaging and public search.
Never return private document URLs, internal moderation notes or sensitive account fields.
6.2 Standard response shapes
Success: { "data": { ... }, "meta": { "requestId": "..." } }Error:   { "error": { "code": "VALIDATION_ERROR", "message": "Check the submitted fields", "fields": {} }, "meta": { "requestId": "..." } }List:    { "data": [ ... ], "page": { "nextCursor": "...", "hasMore": true } }

6.4 Endpoint validation rules
Only public, approved and non-sensitive fields may be returned by public endpoints.
Advisor application requires institution, program, academic stage, eligibility declaration and private evidence upload reference.
Consultation requests require an approved advisor, allowed time window, topic and consent to platform rules.
Only consultation participants may read or send messages in that consultation.
Only eligible authors may submit reviews; eligibility checks must not expose identity evidence publicly.
Admin endpoints require a separate admin permission check and must write audit events.
All list endpoints must enforce maximum page size and safe filter allowlists.
6.5 OpenAPI and API testing
Maintain an OpenAPI 3.1 specification in the repository.
Generate or validate typed clients from the specification where useful.
Add contract tests for authorization, validation, pagination and error shapes.
Publish no internal admin API documentation publicly.
Use seeded non-production data for API demos and automated tests.

Use foreign keys, unique constraints, check constraints and transactions.
Use soft deletion only where audit or legal needs require it; otherwise implement documented deletion/anonymization workflows.

Store currency code with each amount and retain source date for fee estimates.
Store source provenance for every material factual claim.
Keep student identity documents in private object storage; database stores opaque storage keys and review metadata only.
Do not store raw payment data; the MVP has no student payments.

8. Authentication, Authorization and Account Lifecycle
Use one identity provider (Clerk or Supabase Auth) with email verification; evaluate social login as an optional convenience.
Use secure, httpOnly, sameSite cookies where applicable; avoid storing long-lived tokens in localStorage.
Enforce roles and resource ownership on the server for every protected operation.
Support account states: pending verification, active, suspended, deletion requested and deleted/anonymized.
Require re-authentication or step-up checks for sensitive admin actions.
Provide account export/deletion request workflows subject to lawful retention requirements.
Do not permit self-service users to assign themselves advisor, moderator or admin roles.

9. Advisor Verification and Document Handling
Accept only the minimum evidence needed to establish current enrolment and eligibility.
Use private buckets with no public listing; issue short-lived signed download URLs only to authorized reviewers.
Limit document access to assigned verification reviewers; log every access.
Never include evidence documents in advisor public profiles or API responses.
Record verification decision, reviewer, timestamp, reason category and expiry/recheck date.
Delete raw evidence after the documented retention period unless a lawful hold or appeal requires retention.
Support re-verification when enrollment period expires, status is uncertain or a credible report is received.
Allow an advisor to appeal a rejection and submit replacement evidence.
10. Consultation and Messaging Workflow
10.1 State transitions
REQUESTED -> ACCEPTED -> CONFIRMED -> COMPLETEDREQUESTED -> DECLINEDREQUESTED -> CANCELLEDACCEPTED -> RESCHEDULE_PROPOSED -> CONFIRMEDCONFIRMED -> CANCELLED | NO_SHOW | COMPLETED
Only valid transitions are allowed. Store actor, timestamp and reason for state changes. A cancellation policy should define notice windows and repeated no-show handling without creating financial penalties.
10.2 Scheduling requirements
Store requested and confirmed times in UTC and the participant's IANA time zone.
Display time-zone conversions explicitly to both parties.
Prevent overlapping accepted advisor bookings, subject to a configurable buffer.
Use database locking or transactional availability checks to prevent double booking.
Send confirmation, reminder, cancellation and reschedule notifications.
Do not imply that a meeting is confirmed until the advisor accepts and the server commits the state change.
Use external meeting links in MVP; restrict link visibility to consultation participants.
10.3 Messaging controls
Messages are scoped to a consultation and accessible only to its participants and specifically authorized safety staff.
Apply message length limits, rate limits, spam detection and report controls.
Do not expose personal contact details by default.
Define retention, export and deletion rules in the privacy policy.
Provide a way to report harassment, impersonation, unsafe requests or attempts to sell services.
11. Reviews, Moderation and Reputation
Review eligibility must be established without publicly exposing a reviewer's identity documents.
Require disclosure of course/program and approximate study period; avoid unnecessary personal data.
Use structured rating dimensions and free-text prompts.
Keep published reviews immutable in the audit trail; edits create version history.
Provide moderation queue, policy reason codes, appeal and takedown workflow.
Detect spam patterns and duplicate submissions; do not automatically remove a review solely due to sentiment.
Do not create a single university quality ranking in MVP.
Any aggregate rating must show sample size, date range, dimension and minimum sample threshold.

14. Search, Ranking and Recommendation Logic
14.1 Search
Search by university name, alias, campus, city, country, subject and program.
Normalize case and common punctuation; support typo tolerance only after evaluation.
Provide filters for country, degree level, subject, institution type, language and known fee range.
Show why a result matched where useful.
Do not rank results based on payment, commission or institutional promotion.
14.2 Shortlisting
The MVP shortlist should be explainable and rules-based. It may filter institutions by stated preferences and display fit indicators such as subject match, budget compatibility and published eligibility. Each indicator must identify its input data and missing-data limitations. Do not label a student 'eligible' unless official criteria and all required inputs have been checked.
14.3 No opaque ranking
Avoid a single 'best college' score. If a future fit score is introduced, publish the methodology, weights, data freshness, minimum evidence requirements and known limitations. Users must be able to change priorities and understand trade-offs.

16. Privacy and Data Governance
Collect only data necessary for the feature and explain the purpose at collection.
Keep public profile data separate from private identity and verification data.
Define retention periods for raw evidence documents and consultation messages.
Provide user access, correction, export and deletion request processes as applicable.
Document lawful basis/consent and cross-border transfers with qualified legal advice.
Use privacy-safe analytics and redact personal data from error logs.
Restrict staff access by role and business need; periodically review permissions.
Publish a privacy notice that names processors and explains data sharing.
Because Gradastra is intended to serve users internationally, obtain legal review for applicable privacy and child-safety requirements in each launch market. Do not assume one country's consent or retention model satisfies every jurisdiction. Consider age-gating or guardian-consent workflows if serving minors.
17. SEO, Content and Data Quality Engineering
Render public university and country pages server-side with unique titles, descriptions and canonical URLs.
Generate XML sitemaps only for published, sufficiently complete records.
Use robots directives to exclude dashboards, private pages, search result permutations and admin routes.
Use structured data only where it accurately represents visible content and follows search engine policies.
Track source URL, source publisher, retrieval/check date, data owner and expiry/review date for facts.
Flag stale tuition, deadline, placement and visa information; never silently present old values as current.
Provide correction requests on university pages.
Do not bulk-index thin pages created only to capture keywords.

Vertical/managed scaling first; separate workers or search service only when measured need appears.
Resilience
Retries, timeouts, graceful degradation and provider outage messaging.
